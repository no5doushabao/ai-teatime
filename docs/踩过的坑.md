# 踩过的坑

开发过程中真实踩到并修掉的坑，记下来免得重犯。

## 1. 浏览器缓存：改完界面一直显示旧页

`chrome --app` 窗口会缓存页面。更坑的是 **PowerShell 的 `Invoke-WebRequest` 自己也有缓存** ——
用它验证会得到"文件没更新"的错误结论（我就这么被骗过一次，白白排查半天）。

- **验证网页内容用 `curl`**，别用 `Invoke-WebRequest`
- **根治**：启动器给 URL 加时间戳（`?t=20261010161927`），每次都是"新地址"，浏览器想用缓存都没得用

## 2. 推理模型的"思考 token"会吃光输出额度

`gpt-5` 系列是推理模型：它先"想"再"说"，而**思考的 token 也算在 `max_completion_tokens` 里**。
设 1200 时思考就吃光了，**返回空串**（不是报错！）→ 界面上表现成"卡住不出声"。

- 实测：`max_tokens=1200` → 输出 **0 字**；`max_tokens=4000` → 输出 **1194 字**
- 现在默认给 4000，并对空回复自动重试

## 3. 各家参数不统一

GPT-5 系列**不收自定义 `temperature`**（只允许默认值 1），**也不收 `max_tokens`**（要 `max_completion_tokens`）。
`llm_call()` 改成穷举参数组合（`t_tok` / `t_ctok` / `ctok` / `tok` / `t` / `plain`），
撞到"参数不支持"就换下一套，命中后按模型名缓存。

## 4. 空回复必须报警

以前 `llm_call()` 返回空串，代码就直接"说"了句空话 —— 界面上什么都没显示，
看起来像"这个 AI 卡住了"。现在：空回复 → 3 倍预算重试 → 还不行就给一条明确的提示。

## 5. 配置缓存导致"换了议题不生效"

`settings` 是服务启动时读一次的。界面上换了议题、后端还在用旧配置 → 顶栏显示新议题、讨论聊旧的。
**修法**：按下「开始讨论」时重新读一次配置。

## 6. 模型会"越位"替别人发言

模型有时会用别人的口吻写一段，还在开头标 `【千问】` → 界面上看起来像"署名错位"（头像和名字对不上内容）。
**修法**：提示词加"身份纪律" + `strip_leading_tag()` 兜底剥离。

## 7. 日志被覆盖（丢过一次真实数据）

早期 `main()` 每次启动都 `write_text` 重写 `chat-log.md` —— **重启一次服务就冲掉上一场记录**，
丢过一整场 543 行的讨论。现在每场一个文件、精确到秒、同名加序号。

## 8. `.ps1` 必须存成 UTF-8 with BOM

PowerShell 5.1 读**无 BOM** 的 UTF-8 文件时会按 GBK 解码 → 中文注释把语法撑坏 →
`ParserError: Unexpected token`，双击快捷方式毫无反应。

- 存成 `utf-8-sig`（带 BOM）
- ⚠️ **用编辑器/脚本改完 `.ps1` 之后要重新加 BOM**（我一天犯了两次）
- ⭐ 教训：**交付给人双击的脚本，写完必须自己实跑一次**

## 9. 改代码时的手滑（我的）

用 `edit` 插入代码时，如果 `old_string` 只写"函数头 + 下一行"、`new_string` 只写"函数头"，
**等于在删中间的行** —— 我因此误删过两次 `load_settings` 的开头。

- **插入代码时，`old_string` 和 `new_string` 都要包含完整的原代码**
- **改完立刻跑自测**

## 10. 自测要覆盖到新函数

加了 `strip_leading_tag()` 但自测没覆盖它 → 漏了 `import re` 都没发现，直到真跑才崩。
补了三条断言后，**第一次跑就把这个 bug 抓出来了**。新函数顺手加断言，成本极低。

## 11. 本地绝对路径别写进代码

`run.ps1` 里写死过 `C:\Users\<用户名>\.dsh\...\python.exe` —— 既暴露隐私，别人拿到也跑不起来。
改成按优先级探测（环境变量 → 已知位置 → PATH）。
**提交前扫一遍 `sk-` / `C:\Users` / `D:\` 之类的模式。**

## 12. 阿包插话的那一轮会"跳过暂停"

手动模式下每轮讲完都该停下等「▶ 开始下一轮」，但**阿包插过话的那一轮**讲完不停，
按钮根本不出现、直接开了下一轮。阿包 10-11 晚当场看出来的原话：
"第一轮结束的时候顺利的出现了进入下一轮的按钮，但是进入之后，第二轮没有显示这个按钮
而是直接开启了第三轮。"

- **真因**：`run()` 里"阿包插话"分支末尾是一句 `continue` —— 它**绕过了手动模式的等待逻辑**
  （那个 bug 之前的等待代码是写死在主流程尾部的，插话分支走了另一条路）
- **修法**：把"停下 / 收工（结束议题、超预算）"抽成 `RealTable._pause_between_rounds()`，
  普通轮和插话轮**都调它**，两条路只有一份收尾逻辑
- ⭐ **教训**：同一个循环里的两条分支，收尾逻辑必须共用一份 ——
  复制粘贴出来的分支，最容易漏掉后来才加的规则（手动模式是新加的，
  加的时候只想到主流程，忘了插话这条捷径）
- 复现脚本：`_probe/verify-interject-pause.py`（mock LLM，跑 3 轮，
  分别验"普通轮停 2 次 / 插话轮也停 2 次 / 自动模式停 0 次"）

## 13. 新开的日志文件会被当成"上一次"

做「继续讨论」（挑到聊过的议题 → 接着上次聊）时踩的，**两层**：

① 开场流程是**先 `init_log()` 建本场日志、再回头翻"上一次"**，而新建的文件名时间戳是**最新的**
   → "上一次"永远翻到**它自己那个空壳** → 前情提要恒为空。
   **修法**：`build_recap(topic, exclude=_log_path)`，把本场文件排除掉。

② 光排除还不够：最近那场要是"**点了开场、一轮都没跑起来**"的空壳，照样翻不出东西。
   所以 `build_recap()` 改成**一场一场往前翻**，直到翻出有纪要的那场。
   （实测他那 6 场"AI 叛乱"日志里 **5 场是空壳**，真正有内容的是 19:27 那场 —— 不往前翻就等于没有。）

- ⭐ **教训**：写"找最近的那一份"这类代码时，先问自己一句
  **"我刚创建的东西，会不会被自己选中"**
- 验证脚本：`_probe/verify-resume.py`（第 ⑧ 组专门盯这个：本场空壳 + 更早的真记录）

## 14. "排除本场"排除过头了

修完第 13 条当晚，阿包立刻撞上新的一层：**聊完两轮 → 点「继续讨论」→ 界面提示"没翻到上一次的记录"**。
真因有两半，凑在一起才发作：

① `exclude=_log_path` 排的是"当前这个日志路径"。可**同一议题重开时服务端不会新建文件**，
   于是 `_log_path` 恰恰就是**刚聊完那场**（有内容）→ 把要翻的记录本身排除掉了。
② "要不要新建文件"的判断是 `want[:18] not in str(_log_path.name)` —— 拿**议题原文**比**文件名**，
   而文件名里的空格早被 `init_log()` 换成 `-` 了。含空格的议题永远比不中（每次新建、空壳堆积）；
   不含空格的（"善待AI，是否会…"）则一直复用上一场那个**已经有内容**的文件。

**修法**：

- 只有**真的新建了**文件才排除（`fresh` 标志）
- 判断一律走 `log_safe_topic()` 规范名；而且**只有"点了开场没跑起来"的空壳才复用** ——
  已经聊过的文件一律新建，免得两场记录混进同一个文件

⭐ **教训**：**"文件名"和"用户输入"从来不是一回事** —— 空格、非法字符、截断都会被规整过。
要比就得两边都过同一个规范化函数。

- 验证：`_probe/verify-resume.py` 的 ⑨ / ⑨b 两组专门盯这两个分支

## 15. 讨论进行中再点「开场」→ 点了没反应，还把日志搞串

2026-10-12 凌晨，阿包在界面上选新议题点「开场」，我同时用 API 也开了一场 —— 撞在一起：

- **他那场根本没跑起来**，界面上却像是开过了
- **我那场的发言被写进了他的议题日志**：他那边文件名叫新议题，内容却是旧议题的发言

真因两条：

1. 待机线程跑完一场就 `return` 了（`idle_loop` 里 `run()` 之后），而 `start_requested()` 只是
   `_start_event.set()` —— **那个事件没有任何人在接**
2. `broadcast()` 是往**全局 `_log_path`** 写日志的；`start_requested()` 一被调用就 `init_log()`
   切文件 → 还在跑的那一场，后面所有发言都落进了新文件

**修法（两道闸）**：

- `_debating` 标志（由 `RealTable.run()` 用 try/finally 立起 / 放下）：**讨论进行中直接拦住开场**，
  并明确提示「先点 🛑 结束议题」—— 不静默失败，也不替他中断正在说话的人
- `init_log()` 里再兜一层：讨论进行中**拒绝切换**日志文件

⭐ **教训**：**「点了没反应」是最糟的失败方式** —— 它让人以为成功了，于是继续操作，把状态越搅越乱。
**拦住 + 说清楚怎么办，永远比静默吞掉好。**

- 验证：`_probe/verify-debate-guard.py`（15 项：拦住 / 两道闸 / try-finally 复位 / HTTP 返回 ok=false）

## 16. 讨论跑完了，但"待机"没回来 —— 说话没人理

2026-10-12 凌晨，阿包跑完 10 轮闺蜜局，在旁听席说「两位聊的开心吗」——**没人理**。
他截图问：「讨论结束过后是否大家就自动全部休息了，她俩好像看不见我的话了」。

真因跟第 15 条是**同一个**：`idle_loop` 里跑完一场就 `return`，那个线程死了。
他说的话会进 `_boss_inbox`，但**没有任何人在读它**（`RealTable` 只在讨论期间读）。

- 现象上特别容易误判成"她们都休息了"—— 其实她们好着呢，只是**没人在听**
- **修法**：`idle_loop` 跑完一场**回到待机**（`continue`），不是 `return`；
  顺手把 `_start_event.clear()`（消费掉这次开场）和 `_stop_event.clear()` 做掉，
  并重新播报一次「这一场结束了，回到待机 —— 在场：…」
- 连带修：`summarize_debate()` 在 `_last_log_path` 丢了（服务重启会清掉）时，
  去 `logs/` 里挑**最近修改且真有内容**的那个 —— 不然重启之后连"整理刚才那场"都做不了

⭐ **教训**：**「没有人在听」和「大家都不在」看起来一模一样**。
一个长期循环里的 `return`，等于把"待机"这个状态整个取消了。

- 验证：`_probe/verify-idle-return.py`（10 项：跑完活着 / 说话有人回 / 能开第二场 / 重启后仍能整理纪要）
